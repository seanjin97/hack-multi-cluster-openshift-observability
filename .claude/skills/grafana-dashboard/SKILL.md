# Grafana dashboards: generate from the standard

You write a dashboard as Python in the **central dashboards repo**, build its JSON locally, and hand off an MR. CI decides whether it's good enough: its tests enforce the standard. ArgoCD ships what merges. You never need, and must never assume, access to a cluster: no `oc`, no Grafana, no Prometheus.

## Find the repo
Look for the directory holding `standard.py`, `build.py` and `acm-builtin.md`. In the STARFORGE repo it's `platform-tools/grafana/dashboards/`. If you can't find it, ask the user where the central dashboards repo is checked out. Don't recreate the standard.

| File | Use it to |
|---|---|
| `standard.py` | Build every panel. Its helpers, units, thresholds and filters **are** the design standard. Read it first, every time; it changes. |
| `<team>/<name>.py` | Write the dashboard. Define `dashboard = dashboard(title, description, tags, *sections, scope=..., links=...)`. |
| `<team>/<name>.json`, `kustomization.yaml` | Generated by `build.py`. Commit them; never edit them. |
| `acm-builtin.md` | Look up ACM's built-in dashboards offline: titles, panels, and whether they have data. |
| `metrics-allowlist.yaml` | See which extra platform metrics reach the hub. |
| `*/*.py` from other teams | Copy their shape. |

- **Naming:** the path gives the uid, Grafana folder and URL: `sensor-team-1/system_a.py` → `/d/sensor-team-1-system-a` in folder `sensor-team-1`.
  - Team folder: lowercase, dashes.
  - File: snake_case.
  - Never rename either: renaming changes the URL.

## Workflow
1. **Start from the question.** Ask what the team needs to answer, e.g. "Is my CPU limit slowing my requests?". Every extension row is titled with a question, and a panel that answers none is left out.
2. **Read** `standard.py` and one existing dashboard.
3. **Pick metrics that reach the hub.** Use only:
   - metrics an existing dashboard already queries;
   - metrics a built-in in `acm-builtin.md` with data uses;
   - metrics in `metrics-allowlist.yaml`;
   - golden-path app metrics (`http_request_duration_seconds`).

   If a platform metric is missing, add it to `metrics-allowlist.yaml` with a comment naming the panel, and tell the user platform must approve it. If an app metric is missing, the app has to emit it; never fake it in PromQL.

   For a team's own business metric (e.g. `submissions_total{outcome=...}`), follow `doc/app-teams/1-metrics.md` if present in the repo: counters with an `outcome` label, bounded labels, selected with `{APP}` and wrapped in `per_pod(...)`.
4. **Reuse before you build** (see Built-in dashboards).
5. **Write the `.py` with `standard.py` helpers only.** Never call SDK builders directly. If the standard lacks something, stop and tell the user. A change to `standard.py` is a separate, platform-reviewed MR with its own tests, not part of a dashboard.
6. **Build locally:** `uv run build.py`, from the dashboards directory. If it fails, the message names the panel and the rule. Fix the `.py`; never work around the rule.
7. **Run the tests CI will run:** `uv run pytest` must pass. Commit everything `build.py` wrote; CI rebuilds and fails if that changes any file.
8. **Hand off.** Tell the user:
   - the files to commit: `.py`, `.json`, `kustomization.yaml`, and the allowlist if changed;
   - the dashboard's future URL;
   - any panel that may be empty and why (e.g. no 5xx right now);
   - that CI gates the MR and ArgoCD deploys it on merge.

## What CI gates (so you don't have to guess)
| Gate | Command | Fails when |
|---|---|---|
| Tests pass | `uv run pytest` | A dashboard breaks the standard (layout, filters, time windows, units, descriptions, built-in links), or a builder's behaviour changed |
| Build was run locally and committed | `uv run build.py`, then no file may change | `build.py` writes a `.json` that wasn't committed, overwrites a hand-edited one, updates a stale `kustomization.yaml`, or deletes a `.json` whose `.py` is gone |

## Page structure
```
System Vitals    4–6 tiles: is anything wrong right now?           vitals(...)
Golden Signals   Latency | Traffic, then Errors | Saturation       golden_signals(latency=[], traffic=[], errors=[], saturation=[])
Extensions       collapsed rows, one per question                   extension("<question>?", line, ...)
```
- **Layout is automatic:** every line fills the width, with at most 4 graphs or tables per line.
- **Golden Signals quadrants:** 1–3 graphs each. Side-by-side quadrants need counts that wrap alike: 3 + 3 or 2 + 1 works, 3 + 1 doesn't.
- **Placement:** never set widths or positions yourself.

## Filters
- **Every dashboard has five:** cluster → node → namespace → workload → pod.
- **Team dashboards open on their scope:** `scope={"namespace": "<ns>"}`.
- **Wiring a query to the filters:**
  - per-pod metrics: wrap in `per_pod(...)`, which adds `workload` and `node` labels;
  - node metrics: wrap in `per_node(...)`;
  - pod counts: aggregate `SCOPE`.
- **Metrics with no pod or node labels:** end the description with `CLUSTER_ONLY`.
- **Table drill-down:** `links={"pod": drill("cluster", "namespace", "pod")}`.

## Time windows
| Panel | Window | Means |
|---|---|---|
| `graph`, `tile` | `[{RATE}]` | 1-minute points at the 1h default; widens when zoomed out |
| `grid` | `[{RANGE}]` | one value per row for the selected range |
| sizing (`sizing=True`) | `[{RANGE}]` | fixed 7 days, title says "(7d)" |
| peak in a table | `peak(expr)` | highest 1-minute value over the range |

Never hard-code `[5m]`/`[1h]`, and never put a window in a title.

## Built-in ACM dashboards
Check `acm-builtin.md` first, and stop at the first case that fits:
1. **A built-in answers the whole question** (etcd, API SLOs, alert analysis): link it with `links=[builtin("<title>")]`. Don't rebuild it.
2. **The graph is one step in the team's own question:** rebuild it with the helpers, and add "Source: ACM <title>." to the description, so the team never leaves its page mid-investigation.
3. **Never** edit a built-in. Only reuse ones whose "Data here" isn't `none`.

## Design rules the helpers don't do for you
- **Descriptions:** every panel says what it shows and what to do when it's red. They're the runbook.
- **Colour:** pick a threshold set from `standard.py` (`UTILISATION`, `PROVISIONING`, `ERRORS`, `THROTTLING`, `LATENCY`, `PROBLEMS`, `NEUTRAL`), never a colour.
- **Units:** pick from the constants (`PERCENT`, `CORES`, `BYTES`, `BPS`, `PPS`, `SECONDS`, `REQPS`, `COUNT`). Ratios are 0–1 with `PERCENT`.
- **Legends:** include `{{cluster}}`.
- **Tiles:** one number for the selection. Add `or vector(0)` to counts that can be empty.
- **Labels:** keep `by (...)` bounded (cluster, namespace, workload, node, pod, path); never user IDs or raw URLs.
- **Title:** `<Team> - <Scope>`, e.g. `Sensor Team 1 - System A CPU limits`.

## Porting a dashboard built in the Grafana UI
Ask the user for the exported JSON. Read the panels' queries, rewrite them with helpers in a new `.py`, and never paste the JSON.
