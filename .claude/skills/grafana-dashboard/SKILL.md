# Grafana dashboards: compose from the component library

You write a dashboard as Python in the **central dashboards repo**, check it conforms, build its JSON, and hand off an MR. CI decides whether it's good enough. ArgoCD ships what merges. You never need, and must never assume, access to a cluster: no `oc`, no Grafana, no Prometheus.

Three places, three jobs. Know which one you're reading:

| Where | Job | You |
|---|---|---|
| `components/` | **Builds**: panels, layout, queries, units, thresholds, links | compose from it |
| `tests/test_conformance.py` | **Judges**: `check()` holds every machine-checked golden-path rule | run it; read it when it fails; never restate or work around it |
| this skill | **Guides**: the judgement no test can make | follow it |

## Find the repo
Look for the directory holding `components/`, `build.py` and `acm-builtin.md`. In the STARFORGE repo it's `platform-tools/grafana/dashboards/`. If you can't find it, ask the user where the central dashboards repo is checked out. Don't recreate the library.

| File | Use it to |
|---|---|
| `components/` | Build every panel. `from components import *` gives the whole public API (`__all__` in `__init__.py`). Read the module docstrings first, every time; they change. |
| `<team>/<name>.py` | Write the dashboard: `dashboard = dashboard(title, description, tags, *sections, scope=..., links=...)`. |
| `<team>/<name>.json`, `kustomization.yaml` | Generated by `build.py`. Commit them; never edit them. |
| `acm-builtin.md` | Look up ACM's built-in dashboards offline: titles, panels, and whether they have data. |
| `metrics-allowlist.yaml` | See which extra platform metrics reach the hub. |
| `*/*.py` from other teams | Copy their shape. |

- **Naming:** the path gives the uid, Grafana folder and URL: `sensor-team-1/system_a.py` → `/d/sensor-team-1-system-a` in folder `sensor-team-1`. Team folder lowercase with dashes, file snake_case. Never rename either: renaming changes the URL.

## Workflow
1. **Start from the question.** Ask what the team needs to answer, e.g. "Is my CPU limit slowing my requests?". Every extension row is titled with a question; a panel that answers none is left out.
2. **Read** the `components/` docstrings and one existing dashboard.
3. **Pick metrics that reach the hub.** Use only:
   - metrics an existing dashboard already queries;
   - metrics a built-in in `acm-builtin.md` with data uses;
   - metrics in `metrics-allowlist.yaml`;
   - golden-path app metrics (`http_request_duration_seconds`).

   If a platform metric is missing, add it to `metrics-allowlist.yaml` with a comment naming the panel, and tell the user platform must approve it. If an app metric is missing, the app has to emit it; never fake it in PromQL.

   For a team's own business metric (e.g. `submissions_total{outcome=...}`), follow `doc/app-teams/1-metrics.md` if present: counters with an `outcome` label, bounded labels, selected with `{APP}` and wrapped in `per_pod(...)`.
4. **Reuse before you build** (see Built-in dashboards).
5. **Compose the `.py` from `components` only.** Never import the SDK directly. If the library lacks something, stop and tell the user: a new component is a separate, platform-reviewed MR with its own tests, not part of a dashboard.
6. **Check conformance:** `uv run pytest tests/test_conformance.py` from the dashboards directory. `test_team_dashboard_conforms[<team>/<name>.py]` must pass. A failure names the panel and the rule; fix the `.py`. `build.py` doesn't check, so this is the only check before CI.
7. **Build, then run everything CI runs:** `uv run build.py`, then `uv run pytest`. Commit everything `build.py` wrote; CI rebuilds and fails if that changes any file.
8. **Hand off.** Tell the user:
   - the files to commit: `.py`, `.json`, `kustomization.yaml`, and the allowlist if changed;
   - the dashboard's future URL;
   - any panel that may be empty and why (e.g. no 5xx right now);
   - that CI gates the MR and ArgoCD deploys it on merge.

## Design language: the page
```
System Vitals    4–6 tiles: is anything wrong right now?           vitals(...)
Golden Signals   Latency | Traffic, then Errors | Saturation       golden_signals(latency=[], traffic=[], errors=[], saturation=[])
Extensions       collapsed rows, one per question                   extension("<question>?", line, ...)
```
| The metric answers | Put it in |
|---|---|
| "Is it OK right now?" (success rate, backlog, firing alerts) | a Vitals `tile` |
| How long, how much, how often it fails, how full | the matching Golden Signals quadrant |
| A specific question ("Why do submissions fail?", "Which limit to change?") | an `extension` titled with that question |

- **Quadrants:** 1–3 graphs each. Side-by-side quadrants need counts that wrap alike: 3 + 3 or 2 + 1 works, 3 + 1 doesn't.
- **Placement is the library's job:** never set widths or positions.
- **Open on the team's scope:** `scope={"namespace": "<ns>"}`.

## Design language: picking components
| You want | Use |
|---|---|
| One number for the selection | `tile`; add `or vector(0)` to counts that can be empty |
| A trend | `graph`, `{{cluster}}` in every legend |
| A ranking or "which one" | `grid`, sorted by the column that answers the question; `drill(...)` to refilter |
| A sizing answer (requests, limits) | `sizing=True`: fixed 7 days, whatever the time picker says |
| The worst moment in a range | `peak(...)` in a table column |
| Per-pod / per-node metrics | wrap in `per_pod(...)` / `per_node(...)`; pod counts aggregate `SCOPE` |
| Colour | the threshold set that names what the number means: `UTILISATION` (share of capacity), `PROVISIONING` (used / requested), `ERRORS`, `THROTTLING`, `LATENCY`, `PROBLEMS` (any is bad), `NEUTRAL` (no good or bad) |

- **Descriptions are the runbook:** say what the panel shows and what to do when it's red.
- **Labels:** keep `by (...)` bounded (cluster, namespace, workload, node, pod, path); never user IDs or raw URLs.
- **Title:** `<Team> - <Scope>`, e.g. `Sensor Team 1 - System A CPU limits`.

## Built-in ACM dashboards
Check `acm-builtin.md` first, and stop at the first case that fits:
1. **A built-in answers the whole question** (etcd, API SLOs, alert analysis): link it with `links=[builtin("<title>")]`. Don't rebuild it.
2. **The graph is one step in the team's own question:** rebuild it from components, and add "Source: ACM <title>." to the description, so the team never leaves its page mid-investigation.
3. **Never** edit a built-in. Only reuse ones whose "Data here" isn't `none`.

## Porting a dashboard built in the Grafana UI
Ask the user for the exported JSON. Read the panels' queries, rewrite them with components in a new `.py`, and never paste the JSON.
